## Cross-package observations

1. **Real bug, not a style issue**: `pbui-chat`'s Composer "insert object…" button (`Composer.tsx`'s `insertObject()`) calls `pbui.accept({ types: Object.keys(chat.vocabulary.types) })`, which includes a runtime `"message"` type the closed-world type graph never declares. Clicking it throws `runtime type "message" is not declared in the type graph (PBUI-KERNEL-1 C9)` inside `isAcceptable()`, with no error boundary around the story, blanking the whole `#storybook-root`. Confirmed with a standalone Playwright probe (console/pageerror capture). Every Composer story shares the same meta-level `DemoChat` decorator/vocabulary, so this isn't a story-specific fluke — it's a live crash waiting for a real chat session to hit "insert object…" with the full vocabulary. Out of scope to fix here (no source changes), but it blocked the composer-accept-mode and composer-mention-inserted shots entirely.
2. **The Launcher (008) is the one outlier for elevation/shape.** Every other overlay in the system (object menu 001/010/002-chat, accept banner 003, accept chooser 004, refusal notice 006) is flat, square-cornered and shadow-less on a plain white/page background. The Launcher alone gets rounded corners, a drop shadow, and a dimmed backdrop — it reads as if it were pulled from a different, more "modern SaaS" design system than the rest of the family.
3. **The object-menu recipe (black header bar, white body, 1px square border, no shadow) is the strongest consistency win in the audit** — confirmed pixel-identical across core's raw presentation demo (001), core's FileBrowser (010), and pbui-chat's table row and widget title menus (002, 003 chat). Whatever token/component backs this, it's working as intended.
4. **The tan/cream "acceptable" fill is reused well but overloaded.** It marks: an acceptable accept-mode target (core 003, chat 001), a selected FileBrowser row (core 009), a drag-over FileDropZone (core 012), *and* unrelated timeline-entry-kind tags in sandbox (004) and menu keyword tags. Same colour, at least two unrelated meanings (selection/acceptance vs. taxonomy label) — worth deciding if that's deliberate before it multiplies further.
5. **Three-to-four incompatible "something is wrong / unavailable" visual grammars co-exist**: RefusalNotice's red-left-bar banner (core 006), the inline "— reason" text on a disabled menu item (core 002), ProposalCard's chip+accent-bar combo (chat 004), and plotscript's plain red-text error line with no bar or fill (plotscript 001). None share a container recipe.
6. **Sandboxed/native buttons vs. design-system buttons clash inside the same pane.** The Counter program's own "-"/"+" (sandbox 001) render as bare browser buttons (light bevel, native radius) sitting a few hundred pixels from the Inspector's "fire increment"/"fire decrement" (sandbox 002), which are correctly flat/black-bordered pbui buttons. This is expected given the program renders through `UINodeRenderer`, but it's a visible seam a user sees in one screen.
7. **Native form controls (checkboxes, radios) are never re-skinned.** The "directory locked" checkbox (core 006) and the public/developer radios (core 005) render as plain OS-default controls, in contrast to every button, chip, and menu item around them being fully custom-styled. They're the most "unstyled-looking" elements in the whole audit.
8. **Typography is inconsistent by surface family**: monospace for menus/banners/JSON/code (core 001–006, sandbox all, editor, plotscript code panes), bold-uppercase small-caps for tile chrome bars (core 007, plotscript "SCRIPT · DEMO"/"PLOT · DEMO"), and plain proportional sans for the Launcher modal (core 008) and some FileBrowser row labels (core 009). At least three type systems doing the same "chrome label" job across the audit.
9. **CodeEditor has no visible focus state.** Clicking into it (editor 001) changes nothing detectable but the caret — no border-colour change, no outline, no shadow — while every other "now active" affordance elsewhere in the audit (InlineRename 011, accept-mode fills) uses a colour or border change to say so.
10. **A "decided" ProposalCard can visually disagree with its own static story.** Deciding live (chat 004, reject with `danger:true` still set) keeps the red accent bar the static `Rejected` story (which sets `danger:false`) does not show — meaning the static per-story sweep alone understates how a decided-but-still-dangerous proposal actually looks in product.
11. **Tile chrome bar tone-per-app-family is used consistently** (mint/pink in core's Chrome/Kit demo tiles, blue/orange in plotscript's Script/Plot tiles) — the *pattern* (solid pastel bar + bold uppercase label + grip/actions on the right) is shared even though the specific tones differ by app, which looks intentional rather than accidental.
12. **Elevation is used almost nowhere.** Across all 22 screenshots, only the Launcher modal (008) has a box-shadow. Every menu, banner, chooser, and card is a flat 1–2px border on a white background — if elevation is meant to signal "floating above the page," only one component in the family currently does that.
